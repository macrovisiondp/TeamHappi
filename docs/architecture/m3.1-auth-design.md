## 1. What M3.1 delivers

| Area | Implementation |
|---|---|
| Library | **Better Auth 1.7.7**, pinned. Its declared peer ranges cover Next 16.4, React 19.3, Prisma 7.10 and Vitest 5. The compatibility spike passed (§6). Telemetry is explicitly off. |
| Sign-in | Email + password through Better Auth's rate-limited HTTP endpoint (`/api/auth/sign-in/email`). Passwords are 12–128 characters and hashed by Better Auth's built-in hasher; there is no custom cryptography. |
| Account creation | **No public sign-up** (`disableSignUp`, and the endpoint isn't on the allow-list). Accounts are provisioned server-side (`src/lib/auth/provision.ts`). Invitations reuse this in M3.6. |
| Email verification | Required before sign-in. An unverified user who signs in with the correct password gets a fresh 1-hour link. Resending a link returns the same response for unknown, unverified and verified addresses. |
| Sessions | Stored in the database and **checked against it on every request**; there's no cookie cache, so sign-out takes effect immediately. The cookie is `__Secure-teamhappi.session_token`: HttpOnly, Secure, SameSite=Lax, Path=/, signed. Sessions expire after **7 days unused** (refreshed at most daily) and **30 days absolute**, the latter enforced in `validateSession`, which also deletes the session. A new token is issued at every sign-in, so session fixation isn't possible. |
| Server-side validation | `getCurrentUser()` reads the request, validates the session in the database, requires a verified email, and returns only `{ userId, sessionId, name, email }`. The signed-in area gates every route on it, inside `<Suspense>` as Next 16 Cache Components requires. Missing configuration **fails closed**: everyone is treated as signed out. |
| Rate limiting | Stored in the database (`rate_limit` table) with an atomic check-and-increment, so no Redis or paid service is needed. Limits: sign-in 5/min, resend verification 3 per 5 min, verify 10/min, everything else 100/min, per client IP (`x-forwarded-for`, set by Vercel). |
| Endpoint allow-list | Only `POST /sign-in/email`, `POST /sign-out`, `GET /get-session`, `GET /verify-email` and `POST /send-verification-email`. Every other Better Auth endpoint (sign-up, password reset, account linking, session listing and so on) returns **404**, configured or not. |
| Mailer | A development mailer writes the message to the server console; it's for synthetic accounts only and refuses to run in production. The production mailer **refuses and logs nothing**, because the message contains a token. A real provider still needs your decision (D-M3-1, risk R-4). |
| Screens | `/sign-in`, `/verify-email` (resend form) and a sign-out button in the signed-in area. The landing page links to sign-in. All have labelled fields, a live region for errors, and pass axe checks. Error messages never reveal whether an email is registered. |
| Local demo | `npm run dev:db` (local Postgres 18 with the same roles, setup SQL and migrations), `npm run dev:seed` (two synthetic `@example.test` accounts, one verified and one not; credentials only in the git-ignored `.data/dev-accounts.md`), `npm run dev`, then `node scripts/demo-auth.mjs <url>`. |
| Safety guard | `prisma.config.ts` now **refuses any database-touching Prisma command against a non-local host** unless `TEAMHAPPI_REMOTE_MIGRATION=approved` is set. That prevents an accidental `db:migrate` to Neon from `.env.local`. Offline commands (`generate`, `validate`, `migrate diff`) still work. |

## 2. Exact database changes (for review)

### 2a. Setup SQL — `prisma/bootstrap/neon-dev-auth-role.sql` (SHA-256 `e176bb49…cb47f`)

Run once as `neondb_owner` on `teamhappi`, **before** the migration, after approval:

```sql
-- Step 1 (runner substitutes a locally generated password; never shown)
CREATE ROLE teamhappi_auth WITH LOGIN PASSWORD '<generated>'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS NOREPLICATION;
-- Step 2
GRANT CONNECT ON DATABASE teamhappi TO teamhappi_auth;
GRANT USAGE ON SCHEMA public TO teamhappi_auth;
-- Step 3
ALTER ROLE teamhappi_auth SET statement_timeout = '15s';
ALTER ROLE teamhappi_auth SET idle_in_transaction_session_timeout = '15s';
ALTER ROLE teamhappi_auth SET search_path = public;
-- Step 3b (also covers the existing app role; see §3)
ALTER ROLE teamhappi_auth SET timezone = 'UTC';
ALTER ROLE teamhappi_app SET timezone = 'UTC';
-- Step 4: verification SELECT (flags and settings for both roles)
```

### 2b. Migration — `prisma/migrations/20261012120000_auth_foundation/migration.sql` (SHA-256 `c8be0711…c63f2a`)

| Change | Detail |
|---|---|
| New tables | `session`, `account`, `verification`, `rate_limit`. UUIDv7 primary keys; foreign keys to `user` are `ON DELETE RESTRICT ON UPDATE RESTRICT` (no cascade). |
| New indexes | `session_token_key` (unique), `session_user_id_idx`, `session_expires_at_idx`, `account_user_id_idx`, `account_provider_id_account_id_key` (unique), `verification_identifier_idx`, `rate_limit_key_key` (unique), **`user_email_key`** (unique; required by Better Auth's adapter) |
| New constraint | `user_email_lowercase`: `CHECK (email IS NULL OR email = lower(email))`. This keeps the new exact-match unique index equivalent to M2's case-insensitive one. All existing rows on Neon dev are lower-case synthetic addresses. |
| RLS | ENABLE + FORCE on the four new tables, each with one policy `auth_only` **`TO teamhappi_auth`** `USING (true) WITH CHECK (true)`. New policy `auth_identity ON "user" FOR ALL TO teamhappi_auth`. |
| Grants | `teamhappi_auth`: `user` SELECT/INSERT/UPDATE (no DELETE); `session` SELECT/INSERT/UPDATE/DELETE; `account` SELECT/INSERT/UPDATE; `verification` SELECT/INSERT/UPDATE/DELETE; `rate_limit` SELECT/INSERT/UPDATE/DELETE (Better Auth prunes expired rows; found during the local demo). **Nothing** for `teamhappi_app`, and **nothing** on tenant tables for `teamhappi_auth`. |
| Destructive statements | **None.** No DROP, TRUNCATE, DELETE, UPDATE of existing rows, ALTER OWNER or disabling of RLS. |

### 2c. RLS implications

- **Tenant isolation is unchanged.**
  - Every M2 policy is untouched.
  - The app's `user_visible` policy still applies to `teamhappi_app` only.
  - The new `auth_identity` policy applies to `teamhappi_auth` only. Policies are role-scoped, so it doesn't widen what the app role can see.
- **The identity tables are global** (no `tenant_id`), so they're outside the tenant RLS model by design. They're protected by role separation instead: only the auth role has grants, and RLS defaults to deny for every other non-bypass role.
- **The coverage test now checks two roles.** It requires every policy to name exactly one of the two known roles. Identity tables may only have `teamhappi_auth` policies; tenant tables may only have `teamhappi_app` policies. `user` has one of each.

## 3. Finding: Prisma's adapter requires UTC sessions

The spike found that `@prisma/adapter-pg` writes timestamps as UTC wall-clock time **without an offset** and, on read, replaces the offset Postgres returns with `+00:00`. On a connection whose `TimeZone` isn't UTC, every timestamp the app writes or reads is off by that offset.

On a UTC+1 local Postgres, a session whose expiry was set in the past still looked valid and was refreshed. Neon defaults to UTC, which is why M2 on Neon was unaffected.

**Mitigation:**
- `timezone = 'UTC'` is pinned on both login roles (setup step 3b).
- Tests check `current_setting('TimeZone') = 'UTC'` for both roles, and that an expiry written by the app matches the database clock to within seconds.

Setting this on the existing `teamhappi_app` role on Neon is part of the setup approval.

## 4. Rollback

| Situation | Approach |
|---|---|
| The setup SQL or migration fails partway | Each runs in a single transaction and rolls back automatically |
| Unexpected results after it commits | **Preferred:** create a recovery branch `pre-m3.1-…` beforehand, as for M2. A reset needs your separate approval. |
| SQL reversal (destructive, so only with your explicit approval) | `DROP POLICY auth_identity ON "user"`; `ALTER TABLE "user" DROP CONSTRAINT user_email_lowercase`; `DROP INDEX user_email_key`; `DROP TABLE session, account, verification, rate_limit` (these would hold only synthetic data); `REVOKE … FROM teamhappi_auth`; `DROP ROLE teamhappi_auth`; `ALTER ROLE teamhappi_app RESET timezone`; then delete the migration's row from `_prisma_migrations` |

## 6. Better Auth compatibility spike

Better Auth 1.7.7 worked with Next 16.4, Prisma 7.10 (driver adapter) and Postgres 18 **without changing library**. The spike found three issues, all on our side:
1. **Email uniqueness:** Better Auth updates users by email, which Prisma only allows on a field it knows is unique. Fixed by marking `email @unique` (§2b).
2. **UTC sessions:** see §3.
3. **Next 16 prerendering:** the session check reads the clock, which Next flagged during prerender validation. Fixed with `await connection()` (request-time only) and `export const instant = false` on session-gated routes, as the Next 16 authentication guide recommends.

A fourth issue was a missing grant: Better Auth deletes expired `rate_limit` rows, so the auth role needs DELETE on that table (found in the local demo, added to the migration and the exact-grants test).

**Local demonstration** (`node scripts/demo-auth.mjs`, real dev server and local Postgres 18, synthetic accounts): **10 of 10 steps passed**.
1. A signed-out visitor to `/dashboard` is sent to `/sign-in`.
2. The sign-in page renders.
3. A wrong password returns 401.
4. An unknown email returns the same 401.
5. An unverified account returns 403 `EMAIL_NOT_VERIFIED`, and a new link appears in the dev mail log.
6. Public sign-up returns 404.
7. A verified account signs in with an HttpOnly, SameSite=Lax cookie.
8. The dashboard shows "Signed in as Ada Verified".
9. Sign-out succeeds.
10. The old cookie is rejected afterwards.

The dev server log was clean at the end. Running the demo repeatedly within a minute correctly produced 429 from the sign-in rate limit.

**Not adopted:** Better Auth's `nextCookies` server-action flow for sign-in. Calling `auth.api` directly skips the HTTP rate limiter, so the sign-in form posts to the rate-limited endpoint instead.

## 7. Deviations from the M3 plan, and open items

| Item | Status |
|---|---|
| **Nonce-based CSP (plan M3.1)** | **Deferred; needs a decision.** Next 16 can only add nonces to fully dynamic pages, and our Cache Components setup prerenders static shells that can't carry one. Options: (a) make authenticated routes fully dynamic and apply a nonce CSP there; (b) a hash-based CSP; (c) leave it until M3.8 hardening. The current baseline headers are unchanged (`frame-ancestors 'none'`, HSTS and so on). |
| Cookie prefix | `__Secure-` rather than `__Host-` as the plan said. Better Auth sets `__Secure-` when secure cookies are on. Same Secure and HttpOnly protection; `__Host-` would also forbid a `Domain` attribute, which we don't set anyway. |
| Session tokens stored unhashed | See ADR-0008. Mitigated by role separation; hashing is a follow-up. |
| Privileged-role timeouts (30 min / 12 h) | M3.4, together with MFA |
| Password reset, session list and revoke | Not in M3.1 scope; endpoints blocked by the allow-list |
| Email provider | Your decision D-M3-1 is still needed before any non-developer can sign in |
