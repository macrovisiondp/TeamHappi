# M9.2b: CVs on applications

Recruiters can attach a candidate's CV to an application, download it, and remove it. In production the files go to the product owner's private Amazon S3 bucket. In development they go to a local folder, using synthetic files only.

**The product owner's decisions (29 October 2026):**
- One bucket, used for production.
- No malware scanning (GuardDuty) and no KMS keys: S3's built-in encryption (SSE-S3) is enough for CVs.
- No CORS and no domain-specific setup. "The only thing is to make sure those not supposed to have access should not get access to CVs."
- The IAM user gets an S3-only policy now. An SES policy can be added to the same user later, once there's a domain.

## What it does

- **CV section** on each application page:
  - **Shows:** each CV's file name, type (PDF or Word), size, who uploaded it and when.
  - **Download** is available to everyone who can open the application:
    - owners, admins and HR;
    - recruiters;
    - site managers at the vacancy's site;
    - interviewers, for the candidate they're interviewing.
  - **Upload and Remove** are for people who can manage recruitment at that site (not interviewers).
    - Up to **5 CVs per application** and **4 MB each**.
    - Removal asks for confirmation and can't be undone.
- **Anonymisation** (the retention review) now also deletes every CV for that candidate.
- **Until storage is switched on** for a deployment, the page says "CV uploads aren't switched on yet". No upload is attempted.

## Which files are accepted

- **Checked by content, not by name or browser type:**
  - **PDF**, but not with scripts (`/JavaScript`, `/JS`), launch actions, embedded files or rich media.
  - **Word .docx**, but not with macros or ActiveX. Old `.doc` files are refused.
  - **Anything else** (HTML, images, zips, executables) is refused, with a plain message.
- **This is a filter, not a malware scan.** You decided not to use scanning. The protection that matters is that:
  - files are **always downloaded, never opened inside TeamHappi** (`Content-Disposition: attachment`, `nosniff`, a sandbox CSP);
  - so a bad file can't run on TeamHappi's pages or read anyone's session.
- **File names** are cleaned:
  - no folders, quotes or control characters;
  - at most 150 characters;
  - always ending with the real extension.

## How files move

**Through our server, never straight between the browser and S3.**
- **Why:**
  - the bucket needs no CORS and no public access;
  - the browser never sees a storage address;
  - every download goes through the same permission check and audit.
- **Upload (a server action):**
  1. Check the permission.
  2. Check the file.
  3. Put it in storage under a random key inside the organisation's prefix: `tenants/<organisation>/objects/<random>`.
  4. Record it.

  If recording fails, the file is deleted again.
- **Download** (`/recruitment/cv/<id>`):
  1. Check the permission.
  2. Write the audit event.
  3. Read the file and send it.

  Everyone else, including other organisations, gets "Not found".
- **Remove and anonymise:**
  1. The record is marked `deleting` and its file name is blanked, in the same transaction as the change.
  2. The file is deleted from storage.
  3. The record becomes `deleted`.

  If storage fails, the record stays `deleting` and is retried the next time a CV is removed or a candidate is anonymised in that organisation.
- **Size limit:** server actions now accept requests up to 4.3 MB (`experimental.serverActions.bodySizeLimit`). Vercel accepts at most 4.5 MB per request.

## Which storage is used (ADR-0014)

| Where | Store | When |
|---|---|---|
| Production (Vercel) | Amazon S3 | Only when `APPROVED_LIVE_PROVIDERS` includes `aws-s3` **and** all four `STORAGE_S3_*` variables are set. Otherwise uploads are off. |
| Preview deployments | none | The S3 variables are Production-only, so uploads are off. |
| Your computer and tests | `.data/blob-store/` | Synthetic files only. Refused in production. |

- **Vercel variables** (all Production only):
  - `STORAGE_S3_BUCKET` and `STORAGE_S3_REGION` are plain settings;
  - `STORAGE_S3_ACCESS_KEY_ID` and `STORAGE_S3_SECRET_ACCESS_KEY` are **Sensitive**;
  - `APPROVED_LIVE_PROVIDERS=aws-s3` is the on-switch.
- **Platform Admin's** "credentials set" check now looks for the `STORAGE_S3_*` key names.
- **Each record notes its store** (`aws-s3` or `local-disk`), so a file is always read from where it was written.

**Expected bucket setup** (the product owner's AWS account):
- Block Public Access: on.
- Default encryption: SSE-S3.
- No bucket website or CORS.
- The IAM user may only `s3:PutObject`, `s3:GetObject` and `s3:DeleteObject` on `arn:aws:s3:::<bucket>/tenants/*`.

## Security

- **Tenant isolation:**
  - RLS (ENABLE + FORCE + policy).
  - A composite foreign key to the application.
  - `UNIQUE(tenant_id, id)`.
  - A CHECK that requires every storage key to sit inside its own organisation's prefix.
  - Keys are made on the server from the server-resolved organisation. The browser never supplies a key.
- **No DELETE for the app role.** It may update only the deletion columns (`file_name`, `status`, `deleted_by`, `deleted_at`, `delete_reason`).
- **A trigger** allows only `stored → deleting → deleted` and keeps every other column fixed, for every role.
- **Audit** (ids and codes only, never the file name or contents):
  - `recruitment.cv_uploaded` (document id, type, size);
  - `recruitment.cv_downloaded` (every download);
  - `recruitment.cv_removed`;
  - `recruitment.candidate_anonymised` now also records how many CVs were queued for deletion.
- **AWS code is isolated:** only `src/integrations/storage/s3.ts` may import the AWS SDK (a static test checks this). Storage errors never include the key, bucket or credentials.
- **Synthetic data only** in development and tests.

## Database: `20261103120000_application_documents`

- **One new table, `application_document`.** It is additive: no existing rows change.
- **Rollback** is in the header (drop the table and its trigger function), and is only possible while the table is empty.

## Tests

- **`tests/unit/cv-storage.test.ts`:**
  - the content checks (good PDF and .docx; refused PDF scripts, macros, `.doc`, HTML, images, executables, empty and oversized files);
  - file-name cleaning;
  - the S3 on-switch rules;
  - the local store (keys, no overwrite, refused in production).
- **`tests/security/cv-documents.test.ts`** (as the real app role):
  - who can upload, list, open and remove;
  - other organisations get not-found;
  - the audit has no file names;
  - the limit of 5;
  - anonymisation queues every CV;
  - database posture (no DELETE, fixed columns, keys in prefix, type and size checks, one-way status).
- **`tests/e2e/cv-documents.spec.ts`** (local production build, desktop and mobile, with accessibility checks):
  1. an owner adds an applicant;
  2. a non-CV file is refused;
  3. a synthetic PDF is uploaded and downloaded byte-for-byte as an attachment;
  4. a worker gets 404;
  5. the CV is removed and no longer downloadable.

## Not in this milestone

- **Candidates uploading their own CV** on the public link: M9.3 (R5), with Turnstile and rate limits.
- **Emailing applicants:** M9.4 (R7, SES once there's a domain).
- **Malware scanning or KMS:** declined by the product owner. Revisit if candidates upload files themselves (M9.3).
