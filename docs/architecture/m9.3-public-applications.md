# M9.3: Online applications on the share link

Candidates who open a vacancy's share link, or scan its QR code, can now apply there. Already-printed QR codes keep working.

**The product owner approved this on 29 October 2026, with these choices:**
- **Spam protection:** built-in measures (a hidden trap field, rate limits, one application per email per vacancy). There's no third-party CAPTCHA. Cloudflare Turnstile (free) can be added later if spam appears.
- **Privacy notice:** a plain notice naming the organisation as data controller. **An adviser should check the wording before real candidates use it.**
- **No email to applicants yet:** that comes with M9.4 (SES and a domain).

## What the candidate sees

- **The job details**, as before.
- **An "Apply for this role" form:**
  - first name, last name, email, phone (optional);
  - a CV (optional): PDF or .docx up to 4 MB, checked the same way as staff uploads. It's only offered when CV storage is on;
  - the privacy notice, which can be expanded;
  - a confirmation tick box.
- **After sending:** "Thank you. [Organisation] has your application."
  - If the CV couldn't be stored, the application is still sent and the candidate is told.
  - **A repeat application with the same email looks exactly the same,** so the page never reveals who has applied.
- **"Other ways to apply":** shown if the organisation wrote "How to apply" text.
- **The logo is no longer a link,** so candidates aren't sent into TeamHappi's sign-in.
- **When the vacancy is paused, closed, filled or past its closing date,** the form disappears, as before.

## What the organisation sees

- **The application:** it appears on the vacancy at **Applied**, with:
  - source **Careers page**;
  - a history entry by "System";
  - the CV marked "uploaded by the candidate".
- **The audit trail** records `recruitment.online_application`, with the vacancy id and the privacy notice version only.

## How it's protected

- **No organisation context:** the public page writes only through two SECURITY DEFINER functions. They are executable by the app role only, with a pinned `search_path`.
  - **`app.public_apply`** checks, in order:
    1. the code's format;
    2. the rate limit;
    3. that the vacancy is open and the organisation active;
    4. a cap of 200 online applications per vacancy per day;
    5. duplicates (same email, same vacancy).

    It then creates the candidate, the application (recording the privacy notice version and time), the first history entry and the audit event.
  - **`app.public_apply_attach`** records the CV the server has just stored. It only accepts an application that:
    - was created online in the last 10 minutes;
    - belongs to that organisation;
    - has no CV yet.

    The storage key is built inside the function, within the organisation's prefix. The application id never reaches the browser.
- **Rate limits:**
  - 5 attempts per device per hour (duplicates and failures count);
  - `public_apply_throttle` stores only an **HMAC of the device address**, keyed with the server secret, never the address itself. Rows are kept for 2 days;
  - **no role** has any privilege on that table.
- **Bots:** a hidden "Website" field that people never see. If it's filled in, the server pretends to accept the application and stores nothing.
- **Input checks:** every field is checked on the server (zod) and again by the table constraints. The CV is checked by its content.
- **The page itself:** no cookies, no tracking, and not indexed by search engines.
- **Retention:** online applicants are covered by the existing retention review. Anonymising a candidate also deletes their CV.

## Database: `20261104120000_public_applications`

- **`application`:**
  - two new columns, `privacy_notice_version` and `privacy_notice_at`, which are both set or both empty (CHECK);
  - the app role can't write them directly (no column grant).
- **`application_document.uploaded_by`:** may now be empty, for candidate uploads.
- **New table `public_apply_throttle`:** RLS forced, no policies, no grants.
- **`app.public_vacancy`:** recreated to also return `retention_months`, for the notice. Otherwise unchanged.
- **New functions:** `app.public_apply` and `app.public_apply_attach`.
- **Rollback:** the statements are in the migration's header.

## Tests

- **`tests/security/public-applications.test.ts`** (10 tests, as the app role with no organisation context). They cover:
  - the retention period shown;
  - creating an application at Applied, with the notice version and a System history entry;
  - an audit entry with no personal details;
  - silent duplicates;
  - field and file checks;
  - a candidate CV attached and labelled;
  - the attach function refusing repeats, other organisations, staff-added applications and old applications;
  - closed and unknown links refused;
  - the device rate limit;
  - throttle rows being hashes only, with no role access;
  - the app role unable to write the notice fields.
- **`tests/e2e/public-applications.spec.ts`** (desktop and mobile, with accessibility checks):
  1. A signed-out visitor opens the QR link and is shown the missing-field errors.
  2. They apply with a synthetic CV and see the confirmation.
  3. The owner sees the applicant at Applied, from Careers page, with the CV.

## Not in this milestone

- Emails to applicants or to the hiring team (M9.4).
- Cloudflare Turnstile (only if spam appears; free, but needs a Cloudflare account).
- Custom application questions.
