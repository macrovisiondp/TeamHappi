# M4.1: Real organisation workspaces (design review)

Status: proposed for review (17 Oct 2026). Branch `feat/m4.1-workspaces`.

## 1. What exists today (reviewed)

| Area | State |
|---|---|
| Tenancy | `tenant`, `tenant_membership` (status: invited, active, suspended, left), `role`, `role_permission`, `role_assignment` (`site_id` null = organisation-wide), `site`, `team`, `employee`, `document`. Composite tenant foreign keys everywhere. |
| RLS | ENABLE and FORCE on every tenant table. Each policy is `tenant_id = app.current_tenant_id()`, and that function returns a value only while `app.context_token` matches the current transaction. `user` rows are visible as yourself, or as an active member of the current tenant. |
| Context | `withTenant()` is the only place that sets context, and only transaction-locally. `resolveTenantContext()` checks that the tenant is active and the membership is active *under RLS* before it returns a `TenantContext`. |
| Roles | `teamhappi_app` (NOBYPASSRLS, owns nothing), `teamhappi_auth` (identity tables only), migrator. |
| Auth | `getCurrentUser()` validates the session on the server for every request: database lookup, idle and absolute expiry, verified email. |
| Gap | Nothing links a signed-in user to their organisations. Every tenant table is scoped to one tenant, so the app has **no way to list a user's own memberships** without crossing tenant boundaries. |

## 2. Design

### 2.1 Listing your own memberships: one narrow database function

The migration `20261017120000_workspace_memberships` adds:

```sql
app.my_memberships() RETURNS TABLE (tenant_id, tenant_name, tenant_slug, tenant_status, membership_status)
  SECURITY DEFINER, STABLE, search_path pinned
  WHERE m.user_id = app.current_user_id() AND m.status IN ('active','suspended')
```

- **Rows returned:** only the caller's own memberships. `app.current_user_id()` is set by the server from the validated session and is token-bound to the transaction. Without that context it returns nothing.
- **Columns returned:** only what the organisation switcher needs: id, name, slug and the two statuses. No other tenant data.
- **Access:** `EXECUTE` for `teamhappi_app` only; `PUBLIC` is revoked. It is read-only.
- **Why a function and not an RLS policy:** an extra policy "members can see their own membership rows in every tenant" would widen table access for all queries. The function exposes a fixed, reviewed projection instead.
- **Invited memberships** are excluded until invitations exist (M3.6). Left memberships are excluded.

No tables or columns are created or changed.

### 2.2 Context without a tenant

`withUserContext(client, userId, fn)` sits next to `withTenant` in `with-tenant.ts`, the only file allowed to set context. It sets `app.user_id` and the token, and leaves `app.tenant_id` **empty**. Inside it, every tenant table returns zero rows: the default-deny behaviour is unchanged. The only useful thing it can do is call `app.my_memberships()`.

### 2.3 Workspace resolution, per request, on the server

```
getCurrentUser()            validated session, or redirect to /sign-in
  -> listMemberships()      app.my_memberships() under the user context
  -> pick organisation      cookie preference -> must match an ACTIVE membership in an ACTIVE tenant
  -> resolveTenantContext() re-checks tenant and membership status under RLS (unchanged code)
  -> loadGrants()           role assignments -> permission codes, organisation-wide or per site
  => Workspace { tenant, membershipId, grants }
```

- **The cookie (`teamhappi.org`) is only a preference.** It is HttpOnly, SameSite=Lax, Secure on https, and holds only a tenant id. Every request revalidates it, so a forged or stale value just falls back. **It never grants access.**
- **Switching** is a plain form POST to `/api/v1/workspace/select`. The route:
  - refuses any request whose `Origin` isn't the app's own (CSRF protection, on top of the SameSite session cookie);
  - accepts the submitted tenant only if it is one of the user's usable memberships;
  - sets the preference cookie and ends in a full-page 303 redirect.

  It works without JavaScript. A server action was tried first, but with Next 16 Cache Components the previous route stayed on screen after the redirect, so a full navigation is used instead.
- **No organisation:** an explanation page. It distinguishes "no membership" from "your access to X is suspended" and "X is suspended", and links to the labelled demo.
- **Several organisations and no valid preference:** a selection page.
- **Nothing is cached across requests.** A suspended organisation, a revoked membership or an expired session takes effect on the next request.

### 2.4 Permission boundaries

- **Grants** are `permission code -> "all" | set of site ids`, derived from the user's role assignments in the current tenant (`site_id` null means organisation-wide).
- **People and profiles** need `employee.view`.
  - Organisation-wide: every employee.
  - Site-scoped: only employees whose primary site is in scope.

  The scope is part of the **database query**, not a filter applied afterwards.
- **Dashboard sections** follow the same scope: site counts use `site.view`, people counts use `employee.view`.
- **Out of scope looks the same as missing:** an employee in another tenant, or outside your sites, returns **404**, so their existence isn't revealed.
- **The UI is not the control:** hiding a link in the interface is never the access check.

### 2.5 Screens

| Route | Real workspace | Notes |
|---|---|---|
| `/dashboard` | Sites, active staff, starting soon, teams; staff per site; recent starters | Empty states when the organisation has no data yet |
| `/people` | Directory from `employee`, within scope | Search, site and status filters (pending, active, left) |
| `/people/[id]` | Profile from `employee`, plus site and teams | 404 when out of scope |
| `/organisations` | Choose between memberships | Server-action forms |
| `/demo/*` | The previous synthetic screens | Separate navigation, "Demo workspace" label, no database access |

The header selector shows the real organisation. If you belong to more than one, it lists only your usable memberships.

## 3. Tests

- **Database security (`tests/security/workspaces.test.ts`, real roles, embedded Postgres):**
  - `my_memberships()` returns only your own rows, and nothing without user context;
  - `left` and `invited` memberships are excluded;
  - the function can't be executed by other roles;
  - user context sees no tenant rows;
  - a forged preference falls back;
  - a suspended tenant or membership is refused, including when the change happens between two requests;
  - site-scoped grants restrict the People queries and the profile lookup;
  - cross-tenant profile lookups return null;
  - a user with no grant sees nothing.
- **Unit:** the selection logic and permission maths.
- **Browser (local, synthetic seed):**
  - an owner with two organisations switches between them;
  - a site manager sees only their site;
  - a user with no organisation sees the explanation page;
  - axe accessibility checks on the new pages;
  - sign-out and session loss redirect to sign-in.
