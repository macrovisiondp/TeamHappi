## 2. New tables, indexes and constraints

| Table | Purpose | Indexes and constraints |
|---|---|---|
| `training_course` | The catalogue | `UNIQUE(tenant_id, id)`; one active course per name; CHECKs on name, description and content lengths, category list, type matching method, renewal 1–120 months, warning 0–365 days, positive version |
| `training_requirement` | Rules (organisation, site, job title, person) | `UNIQUE(tenant_id, id)`; one active rule per course and target; composite foreign keys to course, site and employee; CHECKs on scope matching target, due 0–365 days, job-title length |
| `training_record` | Completions | `UNIQUE(tenant_id, id)` and `(tenant_id, employee_id, id)`; composite foreign keys to employee and course; `replaces_id` to the same person's record; CHECKs on expiry on or after completion, lengths, and a void needing who, when and a reason; expiry index |

- **New types:** five enum types. One is `training_record_method`, which has the same three values as `training_completion_method` but is kept separate so records and courses can evolve independently.
- **New function and trigger:** `app.training_record_void_once()` and its trigger on `training_record`. They block DELETE, any change to a record's facts, and any change after a void, **for every role**.

## 3. RLS and grants

- **RLS:** all three tables have ENABLE + FORCE and one `tenant_isolation` policy for `teamhappi_app` only.
- **Grants to `teamhappi_app`:**
  - SELECT and INSERT on all three tables; **no DELETE**.
  - UPDATE only on these columns:
    - **`training_course`:** name, description, category, certificate_expected, validity_months, warn_days, content, content_version, archived_at, updated_at (not kind or completion method);
    - **`training_requirement`:** mandatory, due_days, archived_at, updated_at (not the course or target);
    - **`training_record`:** voided_at, voided_by, void_reason only.
- **No grants** to the sign-in or platform roles.

## 4. Permission changes for existing organisations

The migration adds three codes to `permission`: `training.view`, `training.record` and `training.manage`. It then adds them to the **built-in** roles of **every** organisation:

| Built-in role | Gets |
|---|---|
| Owner, Tenant administrator, HR manager | all three |
| Site manager | `training.view`, `training.record` (their assigned sites only) |
| Recruiter, Worker | nothing |

Custom roles aren't touched. `createTenant()` and `scripts/create-organisation.mjs` give new organisations the same roles.

## 5. Effect on Joemis Kitchen and other organisations

- **What changes:** their built-in roles gain the permissions above. Training appears in the navigation as live, showing an empty catalogue.
- **What doesn't:**
  - no courses, rules or records are created;
  - nobody is required to do anything until an owner, admin or HR manager adds courses and rules;
  - existing onboarding, right-to-work and member data are unchanged;
  - "cleared to start" is unchanged.

## 6. Data migration or backfill

**None.** The tables start empty. Requirements are worked out from rules when read, so nothing needs backfilling now or later.

## 7. Rollback and recovery

- **Atomic:** the migration runs as one transaction. If any statement fails, nothing is applied.
- **While the tables are empty**, it can be reversed with the statements in the migration's header comment:
  - drop the three tables, the function and the five types;
  - delete the `training.%` role-permission and permission rows;
  - delete the migration's row in `_prisma_migrations`.

  That would be a separately approved, reviewed run.
- **Once training data exists, fix forward.** Rolling back would delete real records.
- **Code rollback without a database rollback is safe:** older code doesn't read the new tables, and the extra permissions are unused.
