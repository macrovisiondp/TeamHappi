## Permission updates (the only change to existing data)

The migration adds four rows to the permission catalogue:

| Code | Description |
|---|---|
| `onboarding.view` | View onboarding and its progress |
| `onboarding.manage` | Start onboarding and work through tasks |
| `onboarding.template.manage` | Create and edit onboarding templates |
| `onboarding.signoff` | Give final onboarding sign-off and waive required tasks |

It then adds them to the **built-in** roles of **every organisation**, including Joemis Kitchen:

| Built-in role | Gets |
|---|---|
| Owner, Tenant administrator, HR manager | all four |
| Site manager | `onboarding.view`, `onboarding.manage` (at their assigned sites only) |
| Recruiter, Worker | nothing |

Custom roles aren't touched. Existing site-scoped role assignments stay site-scoped. This matches what `createTenant()` and `scripts/create-organisation.mjs` now give new organisations.

## Rollback considerations

- The migration is additive and runs as one transaction: if any statement fails, nothing is applied.
- **While the new tables are empty** (before anyone uses onboarding), it can be reversed. The exact statements are in the header comment of the migration file:
  - drop the four tables and five types;
  - delete the `role_permission` and `permission` rows for `onboarding.%`;
  - delete the migration's row in `_prisma_migrations`.

  This would be a separately approved, reviewed run, as with every Neon change.
- **Once onboarding data exists**, rolling back would delete real records. Don't do it: fix forward with a new migration instead.
- **Code rollback without a database rollback is safe:** older app versions simply don't read the new tables, and the extra permissions are unused.
