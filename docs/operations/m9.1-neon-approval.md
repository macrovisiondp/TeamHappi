## 2. New tables, indexes and constraints

| Table | Purpose | Key constraints |
|---|---|---|
| `recruitment_settings` | Stage labels and retention period (one row per organisation) | One per tenant; labels a JSON object; retention 3–12 months |
| `vacancy` | Vacancies | Composite foreign keys to site, team and hiring manager; length checks; openings 1–100; pay range consistent (`numeric(10,2)`) |
| `candidate` | People who apply | Email format (no unique email, so no merging); anonymised means no contact details |
| `application` | A candidate applying to a vacancy | One per candidate and vacancy; one per hired employee; stage and outcome always consistent |
| `application_event` | Stage history | Append-only trigger (every role) |
| `application_note` | Notes | Body 1–2000 characters, or redacted; a trigger allows only a one-time redaction |
| `interview` | Interviews | Duration 5–480 minutes; an outcome needs who and when |
| `interview_interviewer` | Who interviews | Composite foreign key to membership; removal by `removed_at` (no delete) |

- **New types:** ten enum types.
- **New functions:** two trigger functions, `app.application_event_immutable` and `app.application_note_redact_only`, with a pinned `search_path` and no PUBLIC execute.

## 3. RLS and grants

- **RLS:** all eight tables have ENABLE + FORCE and one `tenant_isolation` policy for `teamhappi_app` only.
- **Grants to `teamhappi_app`:** SELECT and INSERT on all eight, **no DELETE**, and UPDATE only on these columns:

  | Table | Updatable columns |
  |---|---|
  | `recruitment_settings` | stage_labels, retention_months, updated_by, updated_at |
  | `vacancy` | title, job_title, site_id, team_id, employment_type, description, openings, status, closes_on, hiring_manager_membership_id, pay_min, pay_max, pay_period, updated_at |
  | `candidate` | given_name, family_name, email, phone, anonymised_at, updated_at (not source or creator) |
  | `application` | stage, outcome, rejection_reason, closed_at, hired_employee_id, hired_at, hired_by, updated_at (not candidate or vacancy) |
  | `application_note` | body, redacted_at (redaction only, enforced by trigger) |
  | `interview` | scheduled_at, duration_minutes, format, location, status, outcome, feedback, feedback_by, feedback_at, updated_at |
  | `interview_interviewer` | removed_at |

- **No grants** to the sign-in or platform roles. Platform staff can't read applicant data.

## 4. Permission changes for existing organisations

The migration adds four codes to `permission`: `recruitment.view`, `recruitment.manage`, `recruitment.hire` and `recruitment.settings`. It then adds them to the **built-in** roles of **every** organisation:

| Built-in role | Gets |
|---|---|
| Owner, Tenant administrator, HR manager | all four |
| Recruiter | view, manage (organisation-wide unless their assignment is limited to a site) |
| Site manager | view, manage (their assigned sites only) |
| Worker | nothing (interviewer access comes from being named on an interview) |

Custom roles aren't touched. `createTenant()` and `scripts/create-organisation.mjs` give new organisations the same roles.

## 5. Effect on Joemis Kitchen and other organisations

- **What changes:**
  - Recruitment appears in the navigation as live, showing no vacancies.
  - Built-in roles gain the permissions above. The **Recruiter** role, which until now had only `site.view`, gains recruitment view and manage.
- **What doesn't:** no data is created, and existing staff, onboarding, training and member data are unchanged.
- **People-page code:** the existing "next employee number" logic moved into a shared file, with no change in behaviour (all People tests pass).

## 6. Data migration or backfill

**None.** The tables start empty. Settings rows are created when an organisation first saves its settings; until then, defaults apply (standard labels, 6 months).

## 7. Rollback and recovery

- **Atomic:** the migration runs as one transaction. If any statement fails, nothing is applied.
- **While the tables are empty**, it can be reversed with the statements in its header comment:
  - drop the eight tables, the two functions and the ten types;
  - delete the `recruitment.%` role-permission and permission rows;
  - delete the migration's row in `_prisma_migrations`.

  That would be a separately approved, reviewed run.
- **Once recruitment data exists, fix forward.**
- **Code rollback without a database rollback is safe:** older code doesn't read the new tables.
